# 1. Translations are discovered from locale files, not registered in code

Date: 2026-11-24
Status: accepted

## Context

The game shipped with every visible string written inline in JSX, across
`App.jsx` (1492 lines), the drawers and the mini-games. The Translation mission
asks for a language button, at least one extra language, and explicitly for
"subsequent translations to be trivial".

Two constraints shaped the decision:

- The test environment configured in `vite.config.js` is plain `node`. Anything
  that reaches for `window`, `navigator` or `localStorage` at import time is
  untestable without dragging a DOM into every test file.
- `App.jsx` is the project's main merge-conflict hotspot (see docs/DEBT.md,
  D05). Any i18n design that needs a per-screen registration step would force
  repeated edits to that file.

We considered `react-i18next`, which is the obvious off-the-shelf answer, and a
hand-rolled layer.

## Decision

A small in-house layer, four modules, each with one job:

| Module | Responsibility |
|---|---|
| `src/i18n/translator.js` | pure key resolution, fallback and interpolation |
| `src/i18n/catalogs.js` | discovers `locales/*.json` via `import.meta.glob` |
| `src/i18n/storage.js` | the only module touching `localStorage` |
| `src/i18n/context.js` + `I18nProvider.jsx` | React binding, `useTranslation()` |

Three choices are worth recording:

1. **Locale files are discovered, never listed.** `import.meta.glob` picks up
   `src/i18n/locales/*.json` at build time and each catalog declares its own
   code in `$meta.code`. Adding a language is adding one file: no import, no
   array to extend, no switch to grow. This is what makes the next translation
   trivial, which was the mission's actual requirement.
2. **No library.** `react-i18next` would have brought plural rules, lazy
   loading and an ICU formatter we do not need for a six-skill kids' game, plus
   a dependency to justify and an initialisation step that is hard to keep out
   of the node test environment. The whole hand-rolled layer is under 150 lines
   and fully covered, which is cheaper to defend than a configured dependency.
3. **I/O is injected, not imported.** `I18nProvider` takes `catalogs`,
   `storage` and `systemLanguage` as props with real defaults. Tests drive it
   with an in-memory store and no browser globals, which is the same seam
   policy D06 applies to the rest of the codebase.

Missing keys fall back to the default language, then to the key itself. An
untranslated screen stays readable and the gap is visible in a screenshot,
rather than rendering an empty box.

## Consequences

Good:

- Adding a language is one JSON file. `catalogs.test.js` then fails until that
  file covers every key of `en.json`, so a half-done translation cannot ship.
- The translation logic is unit-tested in the `node` environment: 100% of
  lines, branches and functions, locked by a threshold in `vite.config.js`.
- Extracting the settings drawer forced the first jsdom component tests into
  the project (`jsdom`, `@testing-library/react`). `App.jsx` turned out to
  render under jsdom, which took overall line coverage from 19% to 51%.
- `App.jsx` gained the hook call and one mounted component, nothing more.

Costs and limits:

- No plural or gender handling, and no date or number formatting. The moment a
  string needs "1 badge / 2 badges", this layer needs a `plural()` helper or a
  swap to `Intl.PluralRules`. Recorded as residual debt.
- `import.meta.glob` ties catalog discovery to Vite. Vitest shares the same
  transform, so tests are unaffected, but a future bundler change would have to
  replace that one line in `catalogs.js`.
- Only the settings drawer and the main-menu buttons are extracted so far. The
  mini-games, the achievement drawer and the modals still hold inline English.

## Alternatives rejected

- **`react-i18next`**: the standard answer, rejected on cost against need. It
  is the thing to adopt if plurals, interpolated components or lazy-loaded
  namespaces ever become real requirements.
- **One flat `translations.js` exporting a big object**: simpler to read, but
  every new language means editing a shared file, which is exactly the
  merge-conflict shape we are trying to avoid on this project.
